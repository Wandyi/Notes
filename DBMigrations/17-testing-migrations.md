# Testing Migrations

A migration is the only change in most systems that is deployed to production having been
tested exclusively against a database that resembles production in no relevant way.

This document is about closing that gap. It has four parts: why the usual testing lies, the
one CI job that catches the most dangerous class, the checks that are cheap enough to run on
every migration, and the rehearsals worth doing for the expensive ones.

---

## Why staging lies, specifically

"It worked in staging" is true and uninformative, and it is worth being precise about which
properties staging fails to reproduce, because each one maps to a failure in this collection.

| Staging property | Production | What it hides |
|---|---|---|
| 400,000 rows in `orders` | 521,000,000 | Every duration. A 40 ms statement becomes 70 minutes (`L-03`) |
| No concurrent load | 350 writes/s, 4,200 reads/s | Lock contention, lock queue jams (`L-01`), deadlocks (`W-11`) |
| No long-running queries | A Finance report every hour | The 90-second query your DDL queues behind |
| One application instance | 40 pods, mixed versions during rollout | Every compatibility break (`C-01`, `C-02`) |
| No replicas | 2 readers, 1 logical subscriber | All of doc 08 |
| No CDC | Debezium, 228 events/s | The backfill's 79× flood (`B-04`) |
| Fresh statistics, small tables | Statistics over 521M rows | Plan differences; the backfill's chunk query may choose a different plan |
| Default configuration | Tuned `autovacuum`, `max_wal_size`, pooler | Vacuum behaviour, WAL behaviour |
| Clean data | Nine years of accumulated anomalies | The 1,840 duplicate `idempotency_key` pairs (`L-08`) |

The last row is the one that is hardest to fix and causes the most calendar-time surprises.
Staging's data was generated by a fixture script; production's was generated by nine years of
bugs, partial rollouts, manual corrections and acquisitions. **A constraint that holds on
synthetic data tells you nothing about whether it holds on real data.**

## The one CI job most teams do not have

Doc 01's 14:02 incident had two failures. The lock storm is caught by a linter. The second —
old pods getting `42703` because the schema changed underneath them — is caught by nothing in
a normal pipeline, because **tests run one version of the code against one version of the
schema, and the failure lives in the combination.**

The job that catches it:

```yaml
compatibility:
  steps:
    - name: Apply ALL migrations from this branch to a scratch database
      run: migrate -path ./migrations -database "$SCRATCH_URL" up

    - name: Check out the PREVIOUS production release
      run: git checkout "$(git describe --tags --abbrev=0 --match 'release-*')"

    - name: Run the previous release's tests against the NEW schema
      run: make integration-test DATABASE_URL="$SCRATCH_URL"
      # Old code, new schema. This is the N-1 cell of doc 13's matrix,
      # and it is the state your fleet is in during every rollout.
```

Three variants, and it is worth running all three because they catch different ordering errors:

| Job | Code | Schema | Catches |
|---|---|---|---|
| `compatibility-back` | Previous release | New | A contract migration shipped too early — the common one |
| `compatibility-fwd` | This branch | Previous | An expand migration that was not merged, or ordering reversed |
| `compatibility-skip` | Two releases back | New | Whether your N-2 rollback target still works |

The third matters if you ever roll back more than one release, which most teams claim they can
and few have tested.

**What makes this job work is the previous release's *tests*, not its code.** You are asserting
that the behaviour the old version guaranteed still holds against the new schema. That is
exactly the invariant doc 01 requires, expressed as something a pipeline can check.

**The cost** is an extra CI job of a few minutes and the discipline of keeping integration
tests runnable from a tag. The second part is the real cost, and it is worth paying.

## Cheap checks: run these on every migration

### Lint the statements

Static analysis encodes doc 02's entire table as a build failure. For PostgreSQL, `squawk` and
`eugene`; for MySQL, `skeema lint`; Atlas has its own linter across engines.

The rules worth enforcing, with the scenario each prevents:

| Rule | Prevents |
|---|---|
| Require `lock_timeout` to be set in the migration | `L-01` |
| Ban `ALTER COLUMN ... TYPE` that rewrites | `L-03` |
| Ban adding a `NOT NULL` column without a default | `C-01`, compatibility |
| Require `CHECK ... NOT VALID` before `SET NOT NULL` | `L-08` |
| Require `CONCURRENTLY` on index creation and drops | `L-05` |
| Require `NOT VALID` on new `CHECK` and `FOREIGN KEY` constraints | `L-07` |
| Ban `ADD CONSTRAINT ... UNIQUE` directly | `L-08` |
| Ban `RENAME` of a column or table | `C-01` |
| Ban `DROP COLUMN` without an override comment | `C-01` |
| Ban multiple DDL statements in one file (MySQL/Oracle) | `L-11`, `T-05` |
| Require `ALGORITHM=INSTANT` or `INPLACE, LOCK=NONE` (MySQL) | `L-10` |
| Ban `char(n)`; require `text` or `varchar` | Padding surprises in comparisons |
| Ban `timestamp` without time zone | `C-12` |

Every rule needs an override mechanism, because every rule has legitimate exceptions. The
override should be a comment in the file stating the reason, which makes the exception a thing
a reviewer reads rather than a thing a flag silences:

```sql
-- squawk-ignore ban-drop-column
-- reason: phase 6b of RVB-4471. Column has not been written since 2026-11-12
--         and has not been read since 2026-11-19. 92-day soak complete; the
--         quarterly export ran against the new column on 2027-01-05.
ALTER TABLE orders DROP COLUMN amount_cents;
```

### Replay against a production schema snapshot

Dump production's schema (no data) nightly into a committed file, and apply new migrations
against it in CI. This catches migrations that assume a column only staging has, and it
catches drift (`T-07`) as a build failure rather than a deploy failure.

```
pg_dump --schema-only --no-owner --no-privileges "$PROD_URL" > schema/production.sql
# CI: load schema/production.sql into a scratch DB, then apply new migrations.
```

### The size gate

The linter does not know your table sizes. Commit a nightly snapshot of them and fail the
build when a rewriting or scanning statement targets a table over a threshold without a
reviewed override (doc 04's `T-09`).

### Up, down, up

Run every down migration in CI: apply up, apply down, apply up again, and assert the resulting
schema matches the first. It is the only exercise most down migrations will ever get
(doc 13's `U-04`).

## Expensive checks: the production-sized rehearsal

For anything that rewrites, scans, or backfills a large table, the only honest test is against
production-sized data.

### Getting a production-sized clone

| Platform | Method | Time | Cost |
|---|---|---|---|
| **Aurora** | Fast database cloning — copy-on-write on the shared storage layer | **Minutes, regardless of size** | You pay only for pages that diverge |
| RDS / Cloud SQL | Restore from a snapshot or PITR to a new instance | ~45 min for 1.42 TB | A full second instance for the duration |
| Self-managed | Restore a physical backup | Hours | Disk plus a host |

**Aurora's fast clone is the single most underused capability in this space.** A 1.42 TB clone
in four minutes, costing only the diverged pages, means there is no defensible reason to
rehearse a Riverbend migration on anything smaller. If you are on Aurora and still testing
migrations against a 400,000-row staging database, that is a habit rather than a constraint.

**On the data itself.** A clone contains real customer data, so the clone is production from a
compliance standpoint: same access controls, same retention, same audit. The alternative —
anonymising it — changes the data distribution, which is the thing you were trying to
reproduce, and anonymisation of a 1.42 TB database is itself a multi-hour job. For rehearsal,
keeping it as production-class data under production-class controls is usually both safer and
cheaper than pretending it is not.

### What to measure on the clone

Not "did it work" — you knew that. Measure:

```sql
-- 1. Duration and lock profile of the DDL.
BEGIN;
SET lock_timeout = '2s';
\timing on
ALTER TABLE orders ALTER COLUMN amount_cents TYPE numeric(14,2);
SELECT mode, granted FROM pg_locks WHERE relation = 'orders'::regclass;
ROLLBACK;

-- 2. The backfill's plan, on production statistics.
EXPLAIN (ANALYZE, BUFFERS)
UPDATE orders SET amount = amount_cents / 100.0
 WHERE order_id >= 100000 AND order_id < 105000 AND amount IS NULL;

-- 3. WAL generated per chunk - this is what sets the throttle rate.
SELECT pg_current_wal_lsn();   -- before and after, difference / rows = bytes per row

-- 4. Dead tuples and table growth after 100 chunks.
SELECT n_dead_tup, pg_size_pretty(pg_total_relation_size('orders')) FROM pg_stat_user_tables
 WHERE relname = 'orders';
```

Item 3 is how doc 06's "1.2 KB of WAL per row" stops being an estimate. Everything downstream
of it — the throttle rate, the duration, the replica lag projection — is only as good as that
measurement, and it takes four minutes to make.

### Synthetic load against the clone

A clone with no traffic reproduces the data but not the contention. Replaying a captured
workload against it finds lock contention, deadlocks and plan regressions that a quiet clone
cannot.

- **PostgreSQL**: `pgbench` with a custom script, or replay from `pg_stat_statements` weighted
  by `calls`.
- **MySQL**: `pt-upgrade` or a general query log replay.
- **Either**: a proxy that mirrors a fraction of production traffic to the clone.

Weighted replay from `pg_stat_statements` is the pragmatic version: take the top 50 queries by
`calls`, run them at the observed proportions, and you have reproduced the shape of your
workload in an afternoon. It will not reproduce the Finance report that runs hourly — add that
one by hand, because it is the one that causes `L-01`.

## Gamedays: rehearsing the failures

Testing proves the migration works. A gameday proves you can handle it not working. The items
below each take under an hour and each reliably finds something the first time.

| Exercise | What it reliably finds |
|---|---|
| **Pause the backfill, then resume** | The pause switch is not wired up, or resume restarts from zero |
| **Kill the migration pod mid-chunk** | The cursor and the data disagree; or the job does not restart |
| **Kill it during `CREATE INDEX CONCURRENTLY`** | Nobody knows about invalid indexes (`L-05`) |
| **Fail over the primary during a backfill** | The job does not detect it; the cursor is ahead of the data (`R-08`) |
| **Stop the logical subscriber for an hour** | Nobody is alerting on slot retention (`R-06`) |
| **Run the rollback, for real, on the clone** | The down migration has a syntax error (`U-04`) |
| **Open a long transaction, then run the migration** | The retry loop exhausts; nobody knows to look for `idle in transaction` (`L-02`) |
| **Have the on-call engineer run the runbook from their laptop** | Missing access, missing tooling, missing VPN rule (`P-06`) |
| **Declare a fake incident while a backfill runs** | Nothing pauses it (`P-04`) |
| **Reverse a store cutover on the clone** | The reverse stream was never tested and the mapping is lossy (`M-10`) |

**The last one is the most valuable and the least often done.** A reverse stream that has never
carried traffic is a configuration file, not a capability, and the gameday is the only way to
find out which you have before you need it.

**Run the gameday before the migration, not as an annual exercise.** The items above are
specific to the migration you are about to run, and their value is highest in the week before
it.

## The complete test matrix

Not everything deserves everything. Here is what to run at each level of risk:

| | Small table, additive | Large table, additive | Large table, backfill | Store migration |
|---|---|---|---|---|
| Lint | ✓ | ✓ | ✓ | ✓ |
| Replay from empty | ✓ | ✓ | ✓ | ✓ |
| Replay from production schema | ✓ | ✓ | ✓ | ✓ |
| Up/down/up | ✓ | ✓ | ✓ | n/a |
| Size gate | ✓ | ✓ | ✓ | ✓ |
| Compatibility (old code, new schema) | ✓ | ✓ | ✓ | ✓ |
| Production-sized clone, timed | | ✓ | ✓ | ✓ |
| `EXPLAIN` on production statistics | | | ✓ | ✓ |
| WAL-per-row measurement | | | ✓ | ✓ |
| Synthetic load on the clone | | | ✓ | ✓ |
| Rollback rehearsal, timed | | | ✓ | ✓ |
| Gameday | | | ✓ | ✓ |
| Reverse-stream rehearsal | | | | ✓ |

**The first six rows are the unconditional ones** (doc 15's `P-08`): once they are in the
pipeline they cost nothing per migration and they cover the failures that do not care about
table size. Everything below is paid for per migration and should be, because it is real
engineering time.

## What to take away

1. **"It worked in staging" is true and uninformative.** Staging differs from production in
   nine ways, and each one maps to a specific failure in this collection.
2. **Production's data was generated by nine years of bugs**; staging's by a fixture script. A
   constraint that holds on synthetic data tells you nothing.
3. **The highest-value CI job is "previous release's tests against the new schema."** It is the
   only thing that constructs the old-code/new-schema combination your fleet is in during every
   rollout.
4. **Run all three compatibility directions** — back, forward, and two releases back if you
   claim you can roll back that far.
5. **A linter encodes doc 02's whole table as a build failure.** Every rule needs an override
   that requires a written reason, so exceptions are read rather than silenced.
6. **Replay new migrations against a nightly production schema snapshot**, which turns drift
   into a build failure instead of a deploy failure.
7. **Run every down migration in CI — up, down, up, assert.**
8. **Aurora's fast clone gives you 1.42 TB in four minutes for the cost of diverged pages.** If
   you are on Aurora and still rehearsing against 400,000 rows, that is a habit, not a
   constraint.
9. **Treat the clone as production data** under production controls. Anonymising it destroys
   the distribution you were trying to reproduce.
10. **Measure WAL bytes per row on the clone.** It takes four minutes and every downstream
    number — throttle rate, duration, lag projection — depends on it.
11. **A quiet clone reproduces the data, not the contention.** Weighted replay of the top 50
    queries from `pg_stat_statements` reproduces the shape in an afternoon — and add the hourly
    Finance report by hand, because that is the one that causes the lock storm.
12. **Gameday the specific migration in the week before it**, not as an annual exercise.
13. **Rehearse the reverse stream by actually reversing.** Until it has carried traffic it is a
    configuration file, not a capability.
14. **Make the first six checks unconditional and pay per migration for the rest.**
