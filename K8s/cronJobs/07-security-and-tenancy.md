# Security, Identity, and Tenancy

Scheduled jobs are a security soft spot out of proportion to their size, for three structural
reasons rather than any individual mistake:

1. **They hold the broadest credentials in the cluster.** The jobs that vacuum databases, rotate
   certificates, reconcile billing, and clean up cloud resources need write access to exactly the
   things you care most about. `db-vacuum` has a Postgres superuser. `cert-expiry-audit` can list
   secrets cluster-wide.
2. **Nobody is watching when they run.** `db-vacuum` starts at 04:00 on Sunday. An anomaly in a
   service shows up as user-visible latency within minutes; an anomaly in a weekly job has a
   six-day head start.
3. **They are the ideal persistence mechanism.** An attacker who can create a CronJob has
   scheduled, recurring code execution that survives pod restarts, node replacement, and cluster
   upgrades, and that looks exactly like the other 412 CronJobs in the cluster. It is the
   Kubernetes equivalent of a crontab backdoor, and it is the first thing to look for after a
   compromise — and among the last places people check.

So the security work divides into two halves: **narrowing what a legitimate job can do**, and
**detecting jobs that should not exist**.

## Identity: one ServiceAccount per CronJob

The default is the worst case. If you omit `serviceAccountName`, the pod gets the namespace's
`default` ServiceAccount, with its token mounted — which means every job in the namespace shares
one identity. You cannot tell from an audit log which job did something, you cannot revoke one
job's access without revoking all of them, and any permission granted for one job's needs is
granted to all of them.

```yaml
jobTemplate:
  spec:
    template:
      spec:
        serviceAccountName: invoice-rollup       # its own identity
        automountServiceAccountToken: false      # it never calls the Kubernetes API
```

That second line deserves emphasis, because it applies to **most** jobs. Ask what your job
actually talks to. `invoice-rollup` talks to Postgres. `partner-sftp-export` talks to an SFTP
server. `session-reaper` talks to Redis and Postgres. None of them call the Kubernetes API, so
none of them need a token mounted — and a token that is not mounted cannot be stolen from a
compromised container.

Set `automountServiceAccountToken: false` by default and turn it on deliberately. You can also
set it on the ServiceAccount itself, which is a better place for it if the job's manifest is
generated by something you do not control.

For the minority of jobs that *do* call the API — the Lease-based lock from doc 02, or a cleanup
job — grant precisely what they use:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: payout-settlement-lock
  namespace: billing
rules:
  # Exactly the lock object, nothing else. resourceNames is the difference between
  # "can manage leases" and "can manage this one lease".
  - apiGroups: ["coordination.k8s.io"]
    resources: ["leases"]
    resourceNames: ["payout-settlement-lock"]
    verbs: ["get", "update"]
  - apiGroups: ["coordination.k8s.io"]
    resources: ["leases"]
    verbs: ["create"]        # create cannot be restricted by name: you cannot name what
                             # does not exist yet. This is the one unavoidable widening.
```

`resourceNames` is the most underused field in RBAC and it is exactly right for scheduled jobs,
whose access needs are usually static and known at authoring time.

### ⚠️ The cleanup job with cluster-admin

The pattern to hunt for in your own cluster:

```yaml
# Do not do this.
rules:
  - apiGroups: ["*"]
    resources: ["*"]
    verbs: ["*"]
```

It appears in "cleanup" and "housekeeping" jobs, usually because someone was iterating, hit a
permission error, widened the Role to unblock themselves, and never came back. The result is a
recurring pod with full cluster control, running unattended, whose image is rebuilt by CI without
security review. If that image's base layer is ever compromised, so is the cluster.

Find them:

```bash
# Every ClusterRoleBinding whose ClusterRole is cluster-admin, with the subject.
kubectl get clusterrolebindings -o json | jq -r '
  .items[] | select(.roleRef.name=="cluster-admin")
  | .metadata.name + " -> " + ([.subjects[]? | .kind+"/"+(.namespace//"-")+"/"+.name] | join(","))'
```

Then narrow each one to the verbs and resources the job actually uses. The honest way to discover
those is to read the code, but the audit log will tell you empirically what it has been doing,
which is a good cross-check against what the code appears to do.

### Cloud credentials

The same logic applies outside the cluster. A job that writes to S3 or calls a payment provider
needs cloud identity, and the two ways to give it differ enormously in blast radius:

- **The node's instance role** — every pod on that node inherits it. A batch pool where one job
  needs S3 write access ends up granting S3 write to every job that lands there.
- **Per-ServiceAccount identity** (IRSA on EKS, Workload Identity on GKE, or the equivalent) —
  the credential is scoped to the ServiceAccount, so `partner-sftp-export`'s identity is not
  reachable from `session-reaper`'s pod even on the same node.

Use the second. The per-job ServiceAccount you already created is the hook it hangs on, which is
another reason not to share `default`.

## Secrets

**Prefer a projected volume or a secrets-store CSI driver over environment variables.** Env vars
are convenient and leak in more ways than people expect: they are inherited by every child
process (including a shell you exec for debugging), they commonly appear in crash dumps and error
reporters that serialise the environment, and anyone with `exec` on the pod can read
`/proc/1/environ`.

```yaml
        volumes:
          - name: partner-key
            secret:
              secretName: partner-sftp-key
              defaultMode: 0400
        containers:
          - name: export
            volumeMounts:
              - name: partner-key
                mountPath: /etc/partner
                readOnly: true
```

⚠️ **Never put a credential in `args` or in a plain `env.value`.** Both are part of the pod spec,
which means anyone with `get pods` in the namespace can read them, and they are captured by every
manifest dump, every `kubectl describe`, and every GitOps diff:

```yaml
# Both of these are readable by anyone who can read the pod.
args: ["--db-password=hunter2"]
env:
  - name: DB_PASSWORD
    value: "hunter2"
```

`secretKeyRef` is fine — the pod spec then contains a reference, not the value.

Rotation deserves its own thought here, because it is F-17's leading cause. A Deployment that
breaks on a rotated secret fails its rollout immediately and loudly. A CronJob has no rollout: the
rotation succeeds, nothing happens, and then the next firing — hours or a week later — fails in a
way nobody connects to the rotation. Two mitigations:

- **A validation step at the top of every job**: connect, authenticate, and fail fast with exit
  code 79 (doc 03's convention) if the credential is rejected. Combined with a `podFailurePolicy`
  that fails the Job immediately on 79, a bad credential becomes an instant page rather than a
  38-minute retry sequence.
- **Trigger a canary run after rotation.** The rotation pipeline should
  `kubectl create job --from=cronjob/...` for every job that consumes the rotated secret and
  check that it succeeds. This converts a delayed failure into an immediate one, which is the
  whole game with scheduled work.

## Pod Security Admission

Most clusters now enforce a Pod Security Standard per namespace. Batch images are the most
frequent violators, because they are often built from a full base image and run as root out of
habit. When a namespace is moved from `audit` to `enforce`, CronJobs are what break (F-06) — and
they break at their next firing, not at the moment of the change.

The `restricted` profile requires, in practice:

```yaml
        securityContext:                    # pod level
          runAsNonRoot: true
          runAsUser: 10001
          seccompProfile:
            type: RuntimeDefault
        containers:
          - name: rollup
            securityContext:                # container level
              allowPrivilegeEscalation: false
              readOnlyRootFilesystem: true  # not strictly required by restricted, but do it
              capabilities:
                drop: ["ALL"]
```

`readOnlyRootFilesystem: true` is worth the extra effort for batch specifically: jobs that write
temp files should write them to an explicit `emptyDir`, which makes the write surface visible in
the manifest rather than implicit:

```yaml
        volumes:
          - name: tmp
            emptyDir:
              sizeLimit: 2Gi          # bounds the damage from a runaway temp file
        containers:
          - name: rollup
            volumeMounts:
              - name: tmp
                mountPath: /tmp
```

⚠️ `sizeLimit` on an `emptyDir` matters more for batch than for services. A job that writes a
large intermediate file can fill the node's ephemeral storage, which triggers disk-pressure
eviction of *other* pods on that node. One badly behaved nightly export can destabilise a node
for everything else running there.

Before flipping a namespace to `enforce`, find out what will break — with `warn` and `audit`
levels first, and then by dry-running the existing templates:

```bash
kubectl label namespace billing \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted
# Then trigger each CronJob manually and look for warnings, rather than waiting for 03:00.
kubectl -n billing create job psa-probe --from=cronjob/invoice-rollup
```

## Network policy

In a default-deny cluster, CronJobs are the workloads most likely to be missing from the
allow-list, because allow-lists are usually built by looking at what is running — and a weekly
job is not running when you look. The symptom arrives at the next firing (F-17).

A job's policy should be written from its actual dependencies:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: partner-sftp-export
  namespace: integrations
spec:
  podSelector:
    matchLabels:
      app: partner-sftp-export         # matches the jobTemplate's pod labels
  policyTypes: ["Egress"]
  egress:
    # DNS. Forgetting this is the single most common NetworkPolicy mistake, and it presents
    # as a name-resolution failure rather than as a policy denial.
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
    # The database, by pod selector.
    - to:
        - podSelector:
            matchLabels:
              app: postgres-primary
      ports:
        - protocol: TCP
          port: 5432
    # The partner's SFTP endpoint, by CIDR, because it is outside the cluster.
    - to:
        - ipBlock:
            cidr: 203.0.113.40/32
      ports:
        - protocol: TCP
          port: 22
```

⚠️ Note that the policy selects on **pod labels**, which come from
`jobTemplate.spec.template.metadata.labels` — not from the CronJob's own labels. A policy written
against the CronJob's labels selects nothing and silently allows nothing, which looks identical to
the job being broken. Label the pod template, and verify:

```bash
kubectl -n integrations get pods -l app=partner-sftp-export   # must match something
```

Egress to a fixed external IP by CIDR is fragile — the partner will change it — so for anything
long-lived prefer routing outbound traffic through an egress gateway or a NAT with a stable
allow-list, and grant the job access to the gateway rather than to the internet.

## Image provenance

Doc 04's F-17 covered mutable tags as a reliability problem. They are also the cleanest supply
chain attack on scheduled work: an attacker who can push to `:latest` gets their code executed on
your schedule, with your job's credentials, at 04:00 on Sunday.

```yaml
# Identity is the digest. The tag is a comment.
image: registry.riverbend.internal/billing/invoice-rollup@sha256:5c1b9e4a7d2f...
```

Digest pinning does three things at once: it makes the running code reproducible, it makes
`imagePullPolicy: IfNotPresent` safe (a cached layer for a digest is by definition the right
layer), and it means a registry compromise cannot change what your job runs without also changing
your manifest — which is in git, reviewed, and diffable.

Beyond pinning, the practices that pay for themselves on unattended workloads:

- **Verify signatures at admission.** A policy controller that requires a valid cosign signature
  from your build system means an unsigned or externally built image cannot run at all.
- **Scan on a schedule, not only at build.** A job that is built once and runs for a year
  accumulates CVEs in an image nobody rebuilds. Rebuild scheduled-job images on a cadence even
  when the code has not changed.
- **Pull from your own registry.** A CronJob pulling from a public registry inherits both its
  availability (doc 04's rate-limit failures) and its trust model.

## Detecting CronJobs that should not exist

This is the second half of the job, and it is the half most teams skip.

An attacker's CronJob does not look unusual. It has a plausible name, it lives in a busy
namespace, and it is one of hundreds. So detect it by **difference from the declared state**
rather than by appearance:

```bash
# Every CronJob not managed by your GitOps tool. On an Argo CD or Flux cluster this list
# should be empty or a short, known set of exceptions.
kubectl get cronjobs -A -o json | jq -r '.items[]
  | select((.metadata.labels["app.kubernetes.io/managed-by"] // "") == "")
  | .metadata.namespace + "/" + .metadata.name
    + "  created=" + .metadata.creationTimestamp'
```

Complement it with structural red flags, which are worth alerting on regardless of provenance —
legitimate jobs rarely need any of these:

```bash
kubectl get cronjobs -A -o json | jq -r '.items[]
  | .metadata.namespace as $ns | .metadata.name as $n
  | .spec.jobTemplate.spec.template.spec as $p
  | select(
      ($p.hostNetwork == true) or ($p.hostPID == true) or
      ([$p.volumes[]? | select(.hostPath)] | length > 0) or
      ([$p.containers[]? | select(.securityContext.privileged == true)] | length > 0)
    )
  | "\($ns)/\($n)"'
```

A CronJob with `hostPath: /`, `privileged: true`, or `hostNetwork` is either a node-management
tool you know about or a serious finding. There is very little in between.

Two more layers:

- **Audit log alerting on `create`/`update` of `cronjobs.batch`** by any subject other than your
  GitOps service account. This is the highest-signal detection available, because the legitimate
  write path is narrow and known.
- **RBAC hygiene**: `create` on `cronjobs.batch` or `jobs.batch` is effectively "run arbitrary
  code as any ServiceAccount in this namespace", since the job template names the SA. Treat
  granting it as equivalent to granting that SA's permissions. It is the most commonly
  underestimated verb in a namespace-admin role.

## Tenancy: 38 namespaces, 30 teams

Fleet-scale ownership needs to be mechanical, not remembered:

- **Namespace per team**, with a `ResourceQuota` (doc 06) so one team's runaway job cannot starve
  another's, and a `LimitRange` so a template with no resources still gets sane defaults.
- **Mandatory ownership labels**, enforced at admission. When a job has been failing for three
  days, the first question is who owns it, and the answer must be in the object:
  ```yaml
  metadata:
    labels:
      app.kubernetes.io/name: invoice-rollup
      app.kubernetes.io/managed-by: argocd
      riverbend.io/team: billing-platform
      riverbend.io/tier: critical          # drives alert routing, doc 08
    annotations:
      riverbend.io/runbook: "https://wiki.riverbend.io/runbooks/invoice-rollup"
      riverbend.io/oncall: "#billing-oncall"
  ```
- **A policy that rejects a CronJob without them.** Doc 10 shows this as a ValidatingAdmissionPolicy
  together with the other fleet-wide requirements.

The runbook annotation is not bureaucracy. At 03:00, the difference between a five-minute
resolution and a two-hour one is usually whether the person paged can find out what the job is
for.

## What to take away

1. Scheduled jobs hold your broadest credentials and run when nobody is watching. Treat them as
   privileged workloads, not as scripts.
2. One ServiceAccount per CronJob, never `default`, and `automountServiceAccountToken: false`
   unless the job genuinely calls the Kubernetes API — most do not.
3. Use `resourceNames` in Roles. A scheduled job's access needs are static and known, which is
   exactly the situation RBAC's narrowest feature was built for.
4. Hunt for the cleanup job with `cluster-admin`. It exists, it was a temporary unblock, and it is
   recurring code execution with full cluster control.
5. Secrets go in projected volumes, never in `args` or a plain `env.value` — both are readable by
   anyone who can read the pod.
6. Credential rotation breaks CronJobs on a delay. Validate credentials at job start with a
   distinct exit code, and canary-run affected jobs as part of the rotation.
7. NetworkPolicy and Pod Security changes break CronJobs at their *next firing*, not when you make
   the change. Trigger jobs manually to test policy changes rather than waiting.
8. Pin images by digest. A mutable tag on an unattended job is both a reliability hazard and the
   cleanest supply chain attack available.
9. Detect CronJobs by difference from declared state, alert on `hostPath`/`privileged`/`hostNetwork`
   in a job template, and audit-log CronJob creation outside your GitOps path. A backdoor CronJob
   looks exactly like the other 412.
10. `create` on `jobs.batch` is arbitrary code execution as any ServiceAccount in the namespace.
    Grant it accordingly.
